**Audited:** `SanamBhanuPrakash/Yoo`, branch `claude/valuable-paid-product-6o7ayj`,
at `e386257` (22 September 2026) — the state the repository was in when this

Sections of the brief that have no subject in this repository: the glass

**On the PDF/image/Office question specifically**, since that was the thing you
were most sceptical about: it is possible in an extension without a backend —
`DecompressionStream` gives you DOCX/XLSX/PPTX and PDF FlateDecode natively, so
text-layer extraction is real work but not exotic. Scanned images and
image-only PDFs are not, because that needs OCR, and OCR without a cloud API
means shipping a WASM engine of several megabytes with poor accuracy on
screenshots. None of this is implemented here. The current code does not read
attachments at all, and the README correctly says so.

## 2. Verdict

### For `e386257`, the state as audited: **NOT READY.**

Not "ready with conditions". Not ready. Seven ways to get a credential past it
were found by loading it in a browser, and two of them meant the extension was
doing nothing at all while appearing installed and enabled.

The single worst one: **a fresh `git clone` followed by "Load unpacked →
`extension/`" produced an extension that guarded nothing.** `extension/engine/`
was in `.gitignore`, the content script's dynamic import rejected, the async
IIFE died before registering a single listener, and Chrome's own extensions
page showed it enabled with no error and no warning. An AWS access key pasted
into a composer landed in the textarea untouched. The documented install
sequence in the README had a build step in the middle of it; a user who skipped
one line got a security tool that was a decoration.

That is worse than not having the extension. A guard that has stopped working
while still looking installed is trusted, and a tool whose failure mode is
silence has no business being in a store.

### After the work in this session: **READY WITH CONDITIONS.**

All seven leaks are fixed and each fix has a test that fails without it. 49
tests pass. The conditions are not code:

1. **Store listing assets.** You need at least one 1280×800 screenshot. I
   generated functional icons; they are a placeholder mark, not a brand.
2. **The privacy policy must be hosted at a URL** and entered in the Developer
   Dashboard. `PRIVACY.md` in a repository is not what the Chrome Web Store
   asks for.
3. **Nobody has used this on a real site.** Every test here ran against mock
   composers I wrote. ChatGPT, Claude and Gemini all use frameworks whose
   write-back behaviour is the fiddliest part of the code, and that path is
   untested against any of them. See §8.
4. **There is no CI.** 49 tests that nobody runs are 49 tests you will break.

## 4. The fail-open question, taken seriously

You asked me not to say "add a try/catch" but to analyse the security
semantics. Here is the analysis.

**The old ordering, in both handlers:**

```js
const result = scan(text, policy);     // ← anything that throws here
if (result.verdict === 'clean') return;
e.preventDefault();                     // ← never runs
```

This is not a bug in the ordinary sense; it is a **policy decision encoded as
an accident**. The code says: if we cannot determine whether this text is
dangerous, treat it as safe. Every exception in `scan()` — present or future —
is silently converted into a disclosure. The user sees a normal paste. There is
no log, no panel, no indication. The failure is indistinguishable from success.

The right semantics are the opposite, and they are not symmetric with the
usual "fail closed" rule either, because blocking every paste forever would be
its own disaster. The correct trichotomy is:

| State | What it means | What should happen |
|---|---|---|
| clean | inspected, nothing found | let it through silently |
| finding | inspected, something found | stop, show what, offer redact |
| **could not inspect** | **no information** | **stop, say so, offer an explicit override** |

The third state did not exist. It does now: `inspect()` returns `{ok, result}`
or `{ok:false, err}` and never throws, both handlers call `preventDefault()`
*before* anything that can fail, and the failure path renders "Chhanni could
not check this" with the error text and an explicit "Insert it anyway". The
user's content is never lost, and the user is never told nothing.

**Was the old ordering reachable?** I spent real effort trying to make
`scan()` throw and could not, which is a genuine credit to the engine: every
validator is pure and total, the two that parse (`jwtHeader`, `jwtPayload`)
have their own try/catch, and 20,000 generated inputs produced no exception.
The defect was therefore *structural rather than live* — the ordering meant
that any future unprotected throw in `resolveOverlaps`, `line()` or a new
validator would become a silent leak rather than a visible failure. That is
still worth fixing, because the cost of fixing it is twenty lines and the cost
of discovering it the other way is somebody's production key.

**What was live** is the third fail-open: the engine import. That one needed no
exotic input at all. It needed a user who read four lines of the README instead
of five.

## 5. Privacy wording

The distinction you drew is exactly right, and the code was on the wrong side
of it in four places.

| Where | Said | Problem |
|---|---|---|
| `manifest.json` description | "Nothing is ever sent anywhere." | subject is ambiguous; reads as a claim about the prompt |
| panel footer | "Nothing was sent anywhere." | same, at the moment of maximum trust |
| `options.html` lede | "Nothing leaves your browser." | plainly false about the prompt |
| README | "It makes no network calls" | heading was fine; body did not draw the distinction |

Your prompt does leave the browser. It goes to OpenAI, or Anthropic, or Google.
That is the entire reason the user typed it. A tool that stands in that path and
says "nothing leaves your browser" is making a true statement about itself in
language that will be read as a statement about the user's data, and the people
most likely to misread it are exactly the non-technical users the product is
for.

Every one of those now names Chhanni as the subject. The panel footer reads
"Checked on this device. Chhanni made no network request." The options page says
outright that the prompt still goes to the provider. There is a `PRIVACY.md`
that leads with the distinction rather than burying it.

Two things that were already right and deserve saying: `popup`/`options`
already used "Chhanni requests no network permission and makes no network
call", which is precise; and the no-network claim is *enforced by a test*, not
asserted — the suite fails if `fetch`, `XMLHttpRequest`, `sendBeacon`,
`WebSocket` or `EventSource` appears in a shipped file. That is a much stronger
form of promise than a privacy policy, and it is rare. When I needed the panel
stylesheet as text, the obvious implementation was
`fetch(runtime.getURL('panel.css'))` — and I ship it as a generated module
instead specifically so that the dumb-regex guarantee stays true. Keep that
property.

## 6. The release package

You asked whether a human following the repository could upload the wrong
directory and publish the wrong version. The answer at `e386257` was worse than
that: **they could upload a directory that was missing its engine**, because
`extension/engine/` was gitignored and the only thing standing between a clone
and a broken ZIP was one README line.

There is no `dist/`, no packaging script, and no ZIP step. `npm pack` would use
`package.json`'s `files` array — `["src","bin","extension","README.md","LICENSE"]` —
which produces an npm tarball, not a store upload. The store upload is "zip the
`extension/` directory", performed by hand, with no check that it is complete.

Version agreement was fine (`package.json` and `manifest.json` both 0.1.0) and
there is now a test asserting it stays that way. The remaining packaging gap is
that nothing produces the ZIP. I did not add a build script, because what to
include and how to name it is your call; but note that the current state is
"a person remembers to do the right thing", and the last time that was the
design it produced the worst finding in this audit.

## 7. Chrome Web Store

I checked current policy rather than relying on memory.

**Would have been rejected or unpublishable at `e386257`:**

- **No icons at all.** The manifest declared none and no image files existed.
  The store requires a 128×128 store icon plus at least one 1280×800
  screenshot. Fixed (icons), outstanding (screenshot).
- **No privacy policy.** Policy requires one for any product that handles user
  data, and Chhanni reads the user's prompt text. `PRIVACY.md` is new; it still
  needs to be hosted and linked in the dashboard.
- **"Nothing is ever sent anywhere"** in the store description is the kind of
  claim the misleading-claims policy is about — content whose outcome must
  match the expectation it sets. Rewritten.

**Not violations, despite looking like them:**

- The twelve host permissions are individually enumerated and each is justified
  by the single purpose. This is the good pattern, not the suspicious one.
- `optional_host_permissions` is absent entirely, and `https://*/*` appears
  nowhere in a permission — only in `web_accessible_resources`, which is a
  different thing.
- One permission (`storage`), no background worker, no `tabs`, no
  `clipboardRead`, no remote code. This is about as clean as an MV3 submission
  gets.

**One real issue I found that is not a policy violation but is a privacy
defect:** `web_accessible_resources` matched `https://*/*`, which per Chrome's
own documentation lets any website fingerprint the extension — "this allows a
malicious website to fingerprint extensions that a user has installed". Any
page could fetch `engine/rules.js` and learn that this user runs a
secret-scanner. Narrowed to the twelve origins. Note the API forces
`https://github.com/copilot/*` to widen to `https://github.com/*` there, which
is a real if small concession.

Also worth knowing: the August 2026 policy updates tightened disclosure
requirements — data collection limited to the disclosed single purpose,
prominent disclosure of everything collected, proactive notification when
handling changes. Chhanni collects nothing, which makes compliance easy, but
the dashboard questionnaire still has to be filled in honestly and the "I do
not collect user data" certification still has to be made deliberately.

## 9. Does it work perfectly?

No.

It works correctly on the paths I tested, which is a different and much smaller
claim. What is genuinely verified: the checksums, the overlap resolution, the
redaction (including a 5,000-case fuzz asserting no matched secret survives),
the two interception paths, both buttons, the Escape key, frame and shadow-root
coverage, and bounded scan time.

What is unverified and material:

- **No real site has ever been tested.** `writeComposer()` carries a comment
  explaining that React and ProseMirror need different write-back strategies —
  and that comment describes the single most fragile code in the project,
  tested only against a plain `<textarea>` I wrote. On ChatGPT or Claude it may
  desync, or silently restore the secret on the next keystroke.
- **The "Send as-is" resend is a synthetic `KeyboardEvent`.** It worked on my
  mock because my mock listens for `keydown`. A composer that submits via form
  submission or a button click will swallow it, and the user's message will
  simply not send. That is a bad failure: the user chose to proceed and nothing
  happened.
- **The 2-second bypass window** after "Send as-is" disables the Enter guard
  entirely, for everything, not just the message that was approved.
- 30 detectors is a reasonable set, not a comprehensive one. Azure AD, GitLab,
  Datadog, Twilio auth tokens, SSH private keys in OpenSSH format, Kubernetes
  configs, and most regional identifiers outside India and the US are absent.

## 10. Performance

The old email pattern's local part was `[A-Za-z0-9._%+-]+`. On a long run of
those characters containing no `@`, the engine consumed the run, failed,
backtracked, and repeated from the next starting position — quadratic.

```
"1-" × 2500   (5 KB)      36 ms
"1-" × 5000   (10 KB)    131 ms
"1-" × 10000  (20 KB)    545 ms
"1-" × 20000  (40 KB)   2254 ms
"1-" × 40000  (80 KB)   9023 ms
```

This was not a synthetic worry. 40 KB of minified-JavaScript-shaped text
(`a.b.c-d_e%f+g` repeated) measured **1,913 ms in Node and 1,741 ms inside the
real paste handler in Chromium.** Pasting a minified bundle fragment into
ChatGPT to ask what it does is an ordinary thing to do, and at 200 KB it would
have been roughly 50 seconds of frozen tab.

Bounded to RFC 5321 limits (local part ≤ 64, labels ≤ 63). Same input: **15 ms
in Node, 57 ms in the browser.** Scaling is now linear — 160 KB costs 90 ms. A
regression test asserts that 4× the input costs less than 10× the time.

One quadratic path remains, lower-grade: `line()` walks the text from the start
for every finding, so a document with thousands of findings is O(n·f) — 4,000
cards on 4,000 lines costs 650 ms. I left it. It needs a pathological document
to matter and fixing it means restructuring the finding loop, which is a larger
change than this audit should make unasked.

## 12. The test suite

**At `e386257`: 29 tests, genuinely good for what they cover.** The
false-positive tests (order numbers failing Luhn, invoice totals failing
Verhoeff, never-issued SSN ranges, `API_KEY=your-api-key-here`, a plain stack
trace) are the right instinct, and the "no module can make a network call" test
is excellent — a guarantee a reviewer can verify by eye.

What they did not cover is **everything that was actually broken**: nothing
tested the content script, nothing tested the manifest beyond its permissions,
nothing tested that the shipped artifact was complete, nothing tested time
bounds, and nothing tested that the three modes in the options page did what
their labels said. Four of the seven leaks were in code with zero test
coverage, and one (the strict-mode promise) was in code that was *fully* tested
at the engine level and wrong at the product level.

Now 49, with a new `test/shipping.test.js` where every assertion corresponds to
an observed browser failure, plus two seeded fuzz invariants over 25,000 inputs
(offsets always point at the matched text; redaction never leaves a matched
secret behind).

**Still missing: any automated browser test.** The harness I used for this
audit is throwaway. Everything in §3 would silently regress.

## 13. UI and UX

The panel is a flat white card, 39 lines of CSS, dark mode handled,
bottom-right, 420px. It is **better than it needs to be and should not be
redesigned**.


What works: severity colour on the label rather than a badge; the masked value
in monospace next to it; the per-finding note carrying the proof ("Visa, passes
Luhn", "Pairs with a secret key to give full API access"); the primary button
counting what it will do ("Redact 3 and continue"); "Send as-is" deliberately
de-emphasised to a ghost button. A user who has never seen this understands it
in about two seconds.

**On Material 3:** you asked me to evaluate a shift toward it. My answer is
don't, and the reason is not aesthetic. This panel's job is to be legible for
four seconds on top of someone else's UI, on a page you do not control, at the
moment the user is about to make a mistake. Material 3's elevation, tonal
surfaces and state layers are a system for building *a* coherent product
surface; Chhanni is an *interloper* on twelve different product surfaces, half
of which are themselves Material. Adopting M3 would make the warning look like
part of Gemini's chrome on Gemini, which is the opposite of what a security
interruption needs. The current flat card with a 4px severity-coloured left
edge reads as foreign everywhere, consistently — and that is correct. Spend the
effort on the typographic scale (§14) instead.

**What is genuinely weak:**

1. **The panel is unanchored.** It appears bottom-right regardless of where the
   composer is. On a wide screen the user's eye is on the composer and the
   warning is 600 px away.
2. **No "don't ask again for this value."** The allowlist exists but lives in
   the options page. The moment someone wants to allowlist a value is the
   moment the panel is showing it, and there is no control there. This is the
   single highest-value UX addition available.
3. **Only 8 findings shown, then "and N more."** For a CSV paste that is most
   of the information.
4. **No state for "scanned and clean."** Users get no positive signal, ever, so
   they have no way to tell "Chhanni checked and it's fine" from "Chhanni isn't
   running". The §3 case-B failure is a direct consequence of that absence.
5. **No indication on an unsupported site.** Same problem.
6. **The panel overlaps the composer** in the bottom-right on short pages — in
   my own screenshots it covers the third composer entirely.

Remaining issues I did not fix because they are design decisions:

- **Type scale.** 39 lines of CSS contain eight distinct font sizes (11, 11.5,

- **Severity is encoded in colour alone** — `#b3243a` for critical, `#a8620f`

  For a red-green colour-blind user the critical/high distinction is close to
  invisible. The label text does not say "critical" anywhere.
- **No `forced-colors` block**, so in Windows High Contrast the left border
  (the only severity signal at the panel level) will be overridden.

## 15. Product

**Who this is actually for.** The README's instinct is right and sharper than
it realises: *"not careless people — tired people, at 11pm, debugging
something."* That is the persona, and it is an individual developer, not a
company. Everything that is good about Chhanni — zero dependencies, no network,
no account, installs in ten seconds, redacts instead of blocking — serves that
person and nobody else.

**Strongest things about it:**

1. **The redact-don't-block decision.** This is the product. Every enterprise
   DLP tool blocks, and every one of them is routed around. A tool that lets
   the prompt through with placeholders is the only version of this that
   survives contact with a deadline.
2. **Proof over pattern.** Luhn, Verhoeff, mod-97, CRC32 and the never-issued
   SSN ranges are the difference between a tool people keep and a tool people
   mute. The measured false-positive rate backs it up.
3. **The no-network guarantee is testable.** Not a policy — a regex a reviewer
   can run. For a tool that reads credentials this is the whole trust story.
4. **India-first identifiers.** Aadhaar with Verhoeff, PAN with holder-type
   validation, Indian mobile numbers. Nobody in the Western DLP market does
   this properly, and DPDP makes it matter.
5. **One engine, three surfaces.** The rule that stops the paste is the rule
   that fails the pre-commit hook. That is a real architectural asset.

**Biggest product weaknesses:**

1. **Attachments.** Stated in §8. The gap is the most common real leak path.
2. **No positive signal.** The product is invisible when it is working, which
   means it is indistinguishable from broken.
3. **Format, not meaning.** Honest about it, but it caps the addressable
   problem at "credentials and identifiers", which is maybe a third of what
   people actually leak.
4. **Twelve hosts, hand-maintained.** Always behind.
5. **No monetisation path as built.** Local-first with no account is correct
   for trust and leaves nothing to charge for. The CLI and the pre-commit hook
   are where a team-scale product would start, not the extension.

## 16. Competitive position

The category was validated this year: **Akamai acquired LayerX for about $205
million, completing in July 2026**, explicitly for browser-based AI usage
control. Nightfall, Cyberhaven, Prompt Security, Netskope and Zscaler are all
selling some version of "stop employees pasting things into ChatGPT."

Every one of them sells to a CISO. All of them involve a backend, a dashboard,
an admin console, and a policy that someone else wrote about you. Their product
is *visibility for the company*. Chhanni's architecture makes it incapable of
providing that — no telemetry, no server, nothing to put on a dashboard — and
that is the position, not a gap:

> Every tool in this category is a surveillance product sold to your employer.
> This one is a seatbelt you install for yourself, and it cannot report on you
> because it cannot talk to anything.

That is a real wedge and it is defensible, because the moment you add the
dashboard you are competing with Akamai on their terms and losing. The ceiling
is that individuals do not have budgets. The realistic path is bottom-up:
developers install it, the CLI ends up in a pre-commit hook, the hook ends up
in CI, and *that* is the thing a team pays for — without ever adding a network
call to the extension.

## 17. What should not be changed

- **The no-network guarantee, and the test that enforces it.** This is the
  product's only unforgeable claim.
- **Redact-first, with "Send as-is" always available.** Do not make the
  override harder. The moment it is annoying it gets uninstalled.
- **Zero dependencies.** 1,834 lines you can read in an afternoon, in a tool
  that handles credentials, is a feature nobody else can match.
- **Checksums over patterns.** The reason the false-positive rate is what it is.
- **The confidence ladder** (`certain`/`likely`/`possible`) and the fact that
  `possible` findings do not block.
- **The limitations section of the README.** It is the most trustworthy thing
  in the repository.
- **The panel's visual design.** See §13. It is doing its job.
- **The Hindi name and the sieve metaphor.** "A sieve for everything you paste
  into an AI" explains the product in nine words.

## 18. The closing questions

**Would I put this in the Chrome Web Store today?**
At `e386257`, no — it was not functional on a fresh clone. After this session's
work: yes, as a 0.2.0 with the four conditions in §2, and I would say plainly
in the listing that attachments are not inspected.

**Would I trust it with my own `.env`?**
Yes. This is what it is best at, it is the case with the most proof behind it,
and redaction demonstrably removes every matched value.

**With a customer export?**
Partially. It will catch the cards, Aadhaar, SSNs and emails row by row. It
has no notion of a table, the panel will show you eight of four thousand
findings, and I would not rely on it to tell me an export is safe.

**With an HR document?**
No. It catches the identifiers and is blind to the names, salaries, performance
notes and medical details that make the document sensitive.

**With a board document?**
No, and not ever. "Unreleased pricing strategy" has no shape. Nothing
pattern-based will see it, and the README is right to say so.

**With my personal information?**
For structured identifiers — card, Aadhaar, PAN, passport-shaped numbers,
email, phone — yes, with checksum-level confidence. For anything narrative, no.

**Would a non-technical person understand the value in five seconds?**
From the panel, yes — "AWS access key ID … Redact 2 and continue" is
self-explanatory. From the store listing, not yet: there is no screenshot, and
"a sieve for everything you paste into an AI" is a lovely line that does not
say what happens.

**Would the UI feel like a modern Google/Material product?**
No, and it should not. See §13.

**Biggest technical risk?**
That nobody has run this against a real AI site. `writeComposer()` and the
synthetic-Enter resend are the two most fragile pieces of code in the project
and both are untested outside a mock. The second-biggest is that there is no CI,
so the 49 tests protecting all of the above will rot.

**Biggest product weakness?**
Attachments, and the absence of any signal that attachments are not covered.

**Biggest opportunity?**
The CLI and the pre-commit hook. The extension earns trust; the hook is where a
team would pay, and it requires no change to the privacy architecture at all.
